    SSH-Tunneling und erweiterte Nutzung von SSH

    Einführung

    Sichere Fernzugriffe spielen in modernen Netzwerken eine wichtige Rolle. Das Protokoll SSH (Secure Shell) wird häufig verwendet, um verschlüsselte Verbindungen zu Servern aufzubauen und Systeme aus der Ferne zu administrieren. Neben dem eigentlichen Remote-Login bietet SSH jedoch noch weitere Funktionen, beispielsweise die Möglichkeit, Netzwerkverkehr durch einen verschlüsselten Tunnel zu leiten. Dadurch können Daten vor dem Mitlesen geschützt und bestimmte Netzwerkdienste sicher erreichbar gemacht werden.

    Eine wichtige Technik ist das SSH-Tunneling beziehungsweise SSH-Portforwarding. Dabei werden Verbindungen über einen sicheren SSH-Kanal umgeleitet. Je nach Konfiguration können einzelne Ports, ganze Anwendungen oder sogar nahezu der gesamte Netzwerkverkehr über diese Verbindung übertragen werden. Dadurch entsteht ein flexibles Werkzeug, das sowohl für legitime Administrationsaufgaben als auch zur Umgehung von Netzwerkbeschränkungen eingesetzt werden kann.

    In dieser Übung werden die Grundlagen und Einsatzmöglichkeiten von SSH-Tunneling untersucht. Der Schwerpunkt liegt auf dem Dynamic Port Forwarding, bei dem SSH als SOCKS-Proxy genutzt wird. Zusätzlich werden die Unterschiede zwischen SSH-Portforwarding und einem SSH-basierten VPN betrachtet sowie die sicherheitsrelevanten Auswirkungen auf Firewalls und Netzwerke analysiert. Ziel ist es, die Funktionsweise von SSH-Tunneln zu verstehen, deren sinnvolle Einsatzgebiete kennenzulernen und mögliche Risiken aus Sicht der IT-Sicherheit bewerten zu können.

    Ziele

    • Verstehen von Dynamic Port Forwarding und Einsatz als SOCKS-Proxy
    • Unterschied zwischen SSH-Portforwarding und SSH-VPN erklären können
    • Verständnis des Zusammenspiels zwischen SSH und Firewalls
    • Nutzung von SSH ohne interaktive Login-Shell

    Aufgabe Grundkompetenz:

    Die Übung besteht aus einem theoretischen und einem praktischen Teil

    Teil 1 – Theorie (Nachlesen und Verstehen).

    Lies die bereitgestellten Texte zu:

    Artikel 1: Wie hängt SSH mit Firewalls zusammen?

    Firewalls und SSH stehen in einem doppelten Verhältnis: SSH kann eine Firewall schützen helfen, aber genauso gut umgehen. Da ein SSH-Kanal beliebigen TCP-Verkehr transportieren kann, lassen sich unverschlüsselte Dienste wie POP3, IMAP oder HTTP innerhalb einer SSH-Verbindung tunneln und damit verschlüsselt durch ein unsicheres Netz schicken. Aus genau diesem Grund verbieten viele Organisationen mit hohen Sicherheitsanforderungen ausgehende SSH-Verbindungen: ein Benutzer könnte über einen externen SSH-Server beliebigen Verkehr aus dem Firmennetz herausschleusen, und im Firewall-Log wäre nur eine harmlose SSH-Verbindung sichtbar.

    Besonders mit Remote Port Forwarding lässt sich eine Firewall faktisch aushebeln: Ein Rechner hinter der Firewall baut eine ausgehende SSH-Verbindung zu einem öffentlichen Server auf und exportiert dabei einen seiner lokalen Ports (z. B. den lokalen SSH-Dienst) auf den öffentlichen Server. Jeder, der sich anschließend zu diesem Port auf dem öffentlichen Server verbindet, landet hinter der Firewall — ohne dass die Firewall-Regeln das eingehend erlauben würden.

    Auch Lucas weist ausdrücklich darauf hin, dass SSH selbst zur Tarnung anderer Protokolle missbraucht werden kann und sogar in DNS oder HTTP eingebettet werden kann. Aus Administratoren-Sicht ist die einzig vollständige Gegenmaßnahme ein streng inspizierender Web-Proxy plus eine Sperre für DNS-Direktzugriffe — was praktisch oft an Geschäftsanwendungen scheitert. Realistisch bedeutet das: Wer SSH zulässt, muss auch Network Traffic Awareness und Intrusion/Extrusion-Detection betreiben, sonst übersieht er Tunnel-Missbrauch. Aus Anwendersicht gilt: Auch wenn man könnte, darf man Firmen-Firewalls nicht einfach mit SSH umgehen — das ist meistens disziplinar- oder dienstrechtlich relevant.

    Artikel 2: Wie kann man mit SSH ein VPN aufbauen?

    Ein klassisches Port-Forwarding tunnelt nur einzelne TCP-Ports. OpenSSH kann darüber hinaus aber auch einen echten Layer-3-VPN-Tunnel aufbauen, der jeden IP-Verkehr zwischen zwei Standorten transportiert — also nicht nur TCP, sondern z. B. auch ICMP oder UDP. Dafür gibt es auf beiden Seiten ein virtuelles tun-Interface (Tunnel-Interface). Beide Endpunkte hängen sich an dieses Interface; sendet das Betriebssystem ein Paket an das Tunnel-Interface, wird es über die SSH-Verbindung zum anderen Ende geschickt, dort entpackt und an das lokale Tunnel-Interface übergeben.

    Damit das funktioniert, müssen drei Dinge zusammenspielen. Erstens muss der Server in sshd_config die Option PermitTunnel erlauben — für einen normalen Routing-VPN ist point-to-point sinnvoll. Zweitens braucht der Tunnel auf beiden Seiten root-Rechte, weil Routing-Tabellen und virtuelle Interfaces angefasst werden. Drittens müssen beide Seiten IP-Forwarding im Kernel aktivieren (unter Linux z. B. via sysctl net.ipv4.ip_forward=1), damit Pakete von einem Interface auf ein anderes geroutet werden — sonst ist der Server zwar ein Endpunkt, aber kein Router zwischen den Netzen.

    Der eigentliche Tunnelbefehl auf Client-Seite verwendet die Option -w:

    ssh -i /root/.ssh/tunnelkey -f -w0:0 vpnserver.beispiel.at true

    Dabei bedeutet -w0:0, dass auf Client und Server jeweils das Tunnel-Device tun0 verwendet werden soll. -f schickt SSH in den Hintergrund, true ist ein "Dummy"-Befehl, der nur deshalb angegeben wird, weil ssh einen Befehl braucht und true garantiert erfolgreich beendet. Nach dem Verbindungsaufbau muss man auf beiden Seiten den tun0-Interfaces noch IP-Adressen zuweisen und Routen auf die Netze hinter dem jeweils anderen Ende setzen — erst dann ist es ein echtes VPN.

    Wichtig zu wissen: Lucas selbst empfiehlt, für produktive VPNs lieber OpenVPN oder WireGuard zu nehmen. SSH-VPN ist TCP in TCP, was bei Paketverlust zu starker Performance-Verschlechterung führt (sogenanntes TCP-Meltdown). SSH-VPN ist also eher die Notlösung, wenn nur ein einziger TCP-Port nach außen offen ist.

    Artikel 3: Wie führe ich einen Befehl per SSH aus, ohne eine Login-Shell zu öffnen?

    Standardmäßig öffnet ssh user@host eine interaktive Login-Shell. Für Automatisierung (Backup-Skripte, Monitoring, Ansible, einen Tunnel im Hintergrund usw.) ist das aber unerwünscht: Es soll genau ein Befehl ausgeführt werden, danach soll die Verbindung enden. SSH bietet dafür mehrere Optionen, die sich kombinieren lassen.

    Die einfachste Variante ist, den Befehl direkt auf die Kommandozeile zu hängen:

    ssh user@host uptime

    SSH verbindet sich, führt uptime aus, gibt das Ergebnis am lokalen Terminal aus und schließt die Verbindung wieder. Es entsteht zwar serverseitig kurz eine Shell, aber kein interaktiver Login.

    Für reines Tunneling ohne irgendeinen Befehl gibt es die Option -N (kein Befehl ausführen) zusammen mit -f (in den Hintergrund), häufig in Kombination mit einem Forwarding-Flag:

    ssh -fNL 2222:localhost:22 user@host

    Damit wird kein Terminal angefordert, kein Login-Skript ausgeführt, und der Tunnel läuft als Hintergrundprozess. Das ist besonders dann nützlich, wenn der eigene Account auf dem Server überhaupt keine Shell besitzt, aber Forwarding erlaubt ist.

    Serverseitig kann (und sollte) der Administrator solche Zugriffe noch enger einschränken. In der Datei ~/.ssh/authorized_keys kann man vor dem Public Key Schlüsselwörter setzen, die genau regeln, was dieser Schlüssel darf:

    • command="..." — egal, was der Client anfordert, der Server führt ausschließlich diesen Befehl aus. Den Original-Wunsch des Clients findet man in $SSH_ORIGINAL_COMMAND wieder.
    • no-pty — es wird kein Pseudo-Terminal zugewiesen, der Schlüssel kann also nicht für eine interaktive Shell verwendet werden.
    • no-user-rc — das Login-Skript ~/.ssh/rc wird nicht ausgeführt.
    • restrict — verbietet alles auf einmal (Port-, Agent-, X11-Forwarding, PTY, user-rc) und erlaubt nur das, was man explizit wieder freischaltet.

    Ein typischer Eintrag für einen Backup-Account, der wirklich nur ein bestimmtes Skript starten darf, sieht so aus:

    restrict,command="/usr/local/scripts/backup.sh" ssh-ed25519 AAAA... backup@kunde

    Damit kann selbst ein gestohlener privater Schlüssel keinen interaktiven Zugang öffnen.

    Teil 2: Praktische Umsetzung (SOCKS-Proxy)

    SSH startet auf deinem Rechner einen SOCKS-Proxy auf Port 9999. Firefox wird so konfiguriert, dass er alle Anfragen (inkl. DNS) an 127.0.0.1:9999 schickt. SSH nimmt diese Anfragen entgegen, verpackt sie in den SSH-Kanal und der SSH-Server am anderen Ende stellt die Verbindungen ins Internet her.

    Schritt 1: SSH mit Dynamic Forwarding starten

    ssh -D 9999 -N benutzer@server

    Erklärung der Flags:

    • -D 9999 — öffnet lokal Port 9999 als SOCKS-Proxy.
    • -N — führt keinen Remote-Befehl aus, also keine Shell. (Praxis-Bezug zu Teil A3!)

    Optional im Hintergrund: 

    ssh -fND 9999 benutzer@dein-ssh-server

    Prüfe in einem zweiten Terminal mit ss -tlnp | grep 9999, ob der Port aktiv ist

    Schritt 2: Firefox konfigurieren

    1. Firefox öffnen, in die Adresszeile about:preferences eingeben.
    2. Bei "Netzwerk-Einstellungen" auf Einstellungen… klicken.
    3. Manuelle Proxy-Konfiguration wählen.
    4. Bei SOCKS-Host eintragen: 127.0.0.1, Port: 9999, Variante: SOCKS v5.
    5. Häkchen bei DNS über SOCKS v5 weiterleiten setzen — sonst leaken deine DNS-Anfragen am Tunnel vorbei.
    6. HTTP- und HTTPS-Proxy-Felder leer lassen.
    7. Mit OK bestätigen.

    Schritt 3: Tunnel verifizieren

    1. Surfe vor dem Konfigurieren zu https://ifconfig.me und notiere deine eigene IP.
    2. Aktiviere den SOCKS-Proxy in Firefox.
    3. Lade https://ifconfig.me neu. Jetzt sollte die IP-Adresse des SSH-Servers angezeigt werden.
    4. Mache einen Screenshot von beiden Zuständen.
    5. Beende den SSH-Tunnel (im Vordergrund: Strg+C; im Hintergrund: pkill -f "ssh.*-D 9999").
    6. Lade die Seite nochmal — ohne Tunnel sollte Firefox jetzt entweder einen Proxy-Fehler melden oder (wenn du den Proxy zurückgesetzt hast) wieder die ursprüngliche IP anzeigen.
